# Handoff: continuing Agent Orange on another PC

Paste everything below the line into a new Claude Code session opened in this repo.

---

You're picking up Agent Orange work from a session on another PC. Read this whole file before doing anything. Memory from the other PC doesn't come with it, so the rules below are the ones that matter.

## What Agent Orange is

A Windows desktop app (WPF, .NET 10, in `client/`) for making games with AI agents, synced through a small Rust + Postgres server (`server/`). Each project is one game with a folder and a GitHub repo. Its pages cover the game's design: a node-based GDD board, plus Characters, Levels, Assets, Mechanics and References. Agents work on the game through the app and drive the creative tools it sets up, such as Godot, Unreal, Blender, ArmorPaint, Aseprite and Material Maker, over MCP. It isn't a chat box with extras. The app's own screens come first, and agent chat comes later.

## We are dogfooding

This phase is about **using Agent Orange to make three small, complete, original games**: a 2D Godot game, a 3D Unreal game and a web game. The agents are the app's user. A game may be made only *through* Agent Orange. When the app can't do something the game needs, stop the game work and build that feature, so the gaps become the roadmap. Normal tools are fine for building Agent Orange itself.

## How to work (the user's rules)

- **Tiny visible pieces.** Work in a running dev build so the user sees each change. Don't grill the user with questions or mock up the whole app.
- **No automated tests of any kind until v1.** No test suites or scripted test runs.
- **Drive the open dev app yourself** with `tools/drive.ps1`, so you see each change instead of asking the user to look. The user asked for this: "you should be able to drive the dev app completely.. while its open".
  - It works inside the app over a pipe that only this Windows account can open (`client/Headless.Drive.cs`, debug builds only). It never uses the real mouse or keyboard and never captures the screen.
  - Commands are the headless script's (`click "Name"`, `set N "text"`, `wait "text"` or a bare `wait`, `sleep ms`, `texts`, `read` (the whole text of each visible document or agent reply, which `texts` misses), `shot name`, `scroll`, `window "Title"`), plus `show` (opens the main window from the tray, where it can start), `windows`, `names` (what can be clicked), `key Escape|Enter|Home|…` and shortcuts such as `key Shift+A` or `key Ctrl+V`, `hover "Name"`, `focus N` (the Nth text box) or `focus "Board"` (by name), `focused` (where keys go), `pick "Shown" "Item"` (a drop-down), `select "Name"` (a node on the open board, by the start of its name), `nodes` (each node's place, size and name, `*` for selected), `point X Y` / `point off` (where a node added or pasted next goes, as the mouse would say), `move X Y` and `size W` (the selected node, as dragging would), `answer "..."` (what the next dialog gets, such as a file picker or "yes" to a confirmation; with nothing queued the real dialog opens), `press "Name"` (a click on something that isn't a button, such as a picture, sent as a real click arrives: preview events first) and `close` (shuts every open menu).
  - `click` also flips toggle buttons, such as a diff file's header. Real mouse gestures (dragging an edge, zooming a picture) can't be driven, so ask the user to try those.
  - For example: `./tools/drive.ps1 'click Agents' 'window Agents' names 'shot agents'`. Pictures are drawn from the windows, with any open popups, into `%TEMP%\AgentOrange-Drive`.
  - Close any popup you open. Headless mode (`AgentOrange.exe --headless <data> <script> <out>`) is still there for runs that need their own data. Its scripts can `seed` a made-up project of hundreds of tasks and assets, `open` a project's page without asking GitHub, time a change with `timed`, assert with `expect`, `expectnot` and `inview`, and call agents' MCP tools in-process with `mcp` (or `mcpjson`, with the arguments as JSON, for lists; the relay would reach whichever copy of the app is running), then look at what that said with `said`, `notsaid` and `saidunder`, and `keep` a part of it, such as a task's id, for later lines as `$NAME`. `agentsetup` shows what an agent session is given (and what a helper agent is given), `refuses` and `allows` run a shell command past the patch-script hook, `writefile`, `writepicture` and `after` make files appear while a tool waits, `writedoc` saves a document as a person's edit would, `stored` shows tasks and milestones as kept, and `limitstop` and `settleasks` try handoff notes without a real agent (the full list is at the top of `client/Headless.cs`). The checks in `tools/checks/` use these; `./tools/checks/run.ps1` runs them against the dev build. `agent` starts a conversation with no program behind it, `feed` gives it recorded Claude Code or Codex lines, `agentstate` reports how it stands and `agentitems` lists what's in it, with its login. `setting` sets a setting kept on this PC. For real sessions without a real agent, `slowlogin` adds a login whose program is a script that takes a turn slowly, `agentsend` sends a conversation a message as the person does, `agentpick` picks one read as the app started (in a `-again` check), `crash` ends its session and the app at once, and `agentend` ends its program; `detach` starts a program on its own (with `wmi`, through WMI) and `quote` checks arguments put on a command line. For splits across agents, `worklogin` adds a login whose program commits a part's work in its folder (`clash` for a file every part writes; `slowlogin` and `worklogin` with `hold` for their seconds take their turns until `release` names their folder, so a check that looks for a conversation working can't find it already stopped, #126), `mcpas` calls an MCP tool as the conversation with a title calls it, and `parallel` says how a project's splits stand, with its folder's files and commits. `fails` runs a command that has to fail and says why. For titles (#125), `titleanswer` is what a login answers when asked to title a conversation, `titles` lists each with how it came about, and `rename` and `renamerow` rename the check's conversation directly or in its row. For a release partway through a run (#124), `heldbackrun` runs one against a made-up server that updates after so many parts of its log, `heldbacksend` sends what the test PC kept, and `testrunstate lost heldback` makes up a held-back run. A `click` on a conversation's row by a title more than one row has is refused, naming each row by its whole name, in headless scripts and the drive tool alike.

## Running the dev build

```
dotnet watch --project client --non-interactive
```

- **Data:** the dev build keeps its data in `%APPDATA%\AgentOrange-Dev`, separate from the installed app. On a new PC, point the dev build at the same server as the installed app (Settings) so no data is lost.
- **Hot reload:** `client/HotReload.cs` redraws the page after each change. Adding new files, enum members, fields or static data makes `dotnet watch` restart the window.
- **`dotnet watch` crashes** (a NullReferenceException inside its own hot reload) when a save leaves the code not compiling, such as a new file whose callers or callees aren't written yet. The crash closes the dev window. So keep every save compiling: write a new file's members before the code that calls them, or stop `dotnet watch`, make the edits, check with `dotnet build`, then start it again. When it does crash, restart it and tell the user.
- **A restart under `dotnet watch` always ends the old copy** (#90, `client/DevWatch.cs`): a rebuild can't replace `AgentOrange.exe` while it runs, so under watch (`DOTNET_WATCH=1`, never headless) a Ctrl+C or stop signal, a close the person didn't choose on the window (its button, its menu or Alt+F4), or dotnet watch itself ending quits it outright, with no tray and no asking, and ends it 5 s later if a dialog holds that up.
- **The log says how each run ended** (`client/AppLog.cs`): `Started … (process N)` and `Ended (process N)`, and in between every close, hide to the tray (and whether the person chose it), restart, update and Windows signing out. A run with no end line was ended from outside (Task Manager, a dotnet watch restart, Windows) or crashed past writing it down, and the next start notes it as "Ended with no word on why". `tools/checks/run-log.txt` checks it.
- **A reply's blocks are cached** (`AgentMarkdown` keeps blocks it has drawn), so a hot-reloaded change to how replies draw only shows after the agents window is closed and opened again.

   - the character on a sphere with spherical gravity and a following camera;
   - then the planet's look;
   - then the character's model and animation (Blender, then Unreal);
   - then one thing to do.

   Have agents check each slice with `play-and-review` (and `model-facing` for every imported model) before ticking its tasks.
4. **When AO is the problem, fix AO.** That means a missing feature, a confusing screen, a tool that fails, or an agent that can't do something. Then log it in `docs/dogfooding.md` with what was done, and carry on with the game.
5. **The user owns the game's design and its look:** bring them decisions about those, and anything that costs money. Never mark an asset delivered: only the user fills a deliverable.

**Known rough edges to expect:**
- **Agents can't add cards** (#92). Until that's built, an agent can only ask the person to add one, so build it when the game needs it.
- **dotnet watch restarts no longer cut agents short** (#101). The tools AO opens (Unreal included) and agent sessions are started on their own and outlive the app, and the restarted app picks each conversation back up. A request to AO's own tools in flight at that moment is told it may or may not have been done.
- **No two-hour cap:** a background command started by Claude Code stops after two hours, which closes the app (and Unreal). So start `dotnet watch` in its own console window instead: `Start-Process powershell.exe -ArgumentList '-NoExit','-Command','Set-Location <repo>; dotnet watch --project client --non-interactive' -WindowStyle Minimized`. Run only one `dotnet watch`.
- **"New conversation" asks which project first.** The drive tool needs the project picked before typing, or the message goes into the open conversation.
- **Unreal's MCP is large:** about 80 toolsets, and some tool descriptions are around 25 KB. A level is saved with the Asset toolset's `SaveAsset`; there's no tool named for saving a level.
- **Waiting for approvals:** agents ask for approval for shell commands. Read each one before allowing it with the drive tool (`click "Allow PowerShell"`).
- **Unreal opens slowly:** the first open after a restart compiles shaders, and the agent's `open_tool` waits up to ten minutes.
